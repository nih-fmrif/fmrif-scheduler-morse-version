# Introduction

This document provides guidance on setting up this web app to run on a single computer for development or testing. Specific steps often cannot be listed as they would depend too much on a particular computer set up at a given time. General advice is given that should be easy to follow for anyone who has ever ran programs from a command line and installed open source projects before. In general, each section of this document depends on the previous section being completed before continuing.

# Required software

This project relies on other software to be installed before it can be run. Much of it is optional and only needed for development and some only for very specific tasks, such as generating pdf files like this.

First and foremost, a UNIX-like operating system is required. This includes every popular operating system except Windows. There are many options if you are running Windows. The easiest would be a virtual machine, docker container, or setting up WSL2 with an Ubuntu image.

For MacOS, you will likely need a third-party package manager such as brew.

## Postgres

You need postgres version 13 or higher running locally.

In addition to installation it must also be configured so that you can create and connect to databases from the command line without using a password. It may not be necessary to do anything extra here, depending on how its default configuration is set up on your system.

## PyEnv

PyEnv is necessary in two cases

* You will be developing the app
* Your local version of python is older than the version listed in the `.python-version` file in the project root

PyEnv works well once it is installed correctly but is a huge fiasco to install. If you don't need it, do not bother.

If you require PyEnv, once it is installed and working you will need to use it to build a copy of the version of python listed in `.python-version` in the project root.

Once that's set up you should be able to `cd` to the project root and 
run
```sh
$ python --version
```
(per convention the `$` is a stand in for your prompt and not part of the command) and see the same version as contained in `.python-version`. At this point, it's best to close your terminal, open a new terminal and repeat the previous step as PyEnv has a tendency to half install and work fine until you try to use it in a new session. If repeating the steps in a fresh terminal window proceeds correctly it should be good to go.

## PipEnv

Pipenv is necessary to run the web app. It needs to be installed from the version of python that will be running the app. If you're using PyEnv, it suffices to `cd` into the project root before installing. Otherwise, you can install it from anywhere. To install it, run:
```sh
$ pip3 install pipenv
```
or, if that fails,
```sh
$ pip install pipenv
```

Once pipenv is installed, `cd` into the project root and run
```sh
$ pipenv install
```
or, if you will be developing on this project,
```sh
$ pipenv install --dev
```

If you pull changes from the git repository that modify `Pipfile.lock` you will need to run that command again.

Pipenv and postgres will be the only software listed here that will need to be installed on the production server.

## Pandoc and ConTeXt (optional)

Pandoc and ConTeXt are only required if you need to rebuild the documentation pdf files from source. See the comments in `docs/make-docs.sh` for other useful tools.

The ER diagram in `schema.pdf` is generated by `erd`. See `sql/generate-schemapdf.sh` and `sql/README` for more information.

Once installed running
```sh
$ ./make-docs.sh
```
in the `docs` directory will either rebuild the docs (sans the ER diagram) or report errors about additional software you will need to install.

# The database

Before you can do anything with the app, a local copy of the database must be provisioned in the local postgres server you have installed.

There are some missing data files that need to be provided first. See `sql/README` for more information.

Once those files are in place you can `cd` into `sql` and run
```sh
$ ./unsafe-reprovision-db.sh
```
which will create a local db named `scheduler`. There are a few warnings generated during import of the old data but other than that the output should be fairly quiet.

If the `erd` tool and its dependencies are installed this will also generate the ER diagram used in documentation generation.

If multiple people will be running this locally on multiple computers, this only needs to be run on one computer. Exporting the scheduler database on the first computer and importing it into a database named scheduler on subsequent computers will suffice.

If you pull changes from the git repository that modify the schema you will need to run that command again and it will obliterate any changes you have made to the local copy of the db.

# App configuration

See `config.pdf`.

The environment variables described in the above pdf can be set, via pipenv, by including a `.env` file in the project root.

The app will fail safe if you try to run it without the proper configuration. Locally it runs in debug mode so it will display a helpful error message. In production mode it would simply return 500 Internal Error.

## the development server

From the project root, `cd` into `scheduler`. Any of the below will do the same thing:
```sh
$ ./dev-server.sh
```
or
```
$ pipenv run flask run
```
or
```
$ pipenv shell
$ flask run
```

This will start a development server in debug mode on `127.0.0.1:5000` which cannot be accessed over the network but can be accessed on the same machine.

You can open any browser and go to `http://127.0.0.1:5000` now. If all the above steps worked out you should get an access denied message.

In order to use the application you will need to use the `force-login` cli command or a browser extension that lets you set additional HTTP request headers (there are many and they all do the same thing) so you can forge the SiteMinder credentials.

These SiteMinder credentials are read by the app:

* `HTTP_SM_USER` - the AD user name
* `HTTP_USER_EMAIL` - the email address of the user
* `HTTP_NIH_DISPLAYNAME` - the display name

Only `HTTP_SM_USER` is strictly required but it's recommended to set all three to get the full experience.

Note that since the SiteMinder headers are being injected manually and not coming from AD, illegal AD names can be used an hence you can log in as "old" account like `vinai[OLD]`.
